## 3. 精度是怎么量出来的（以及为什么换了工具）

### 一把不依赖任何工具的尺子

对每个拍点取 **±150ms 的平均起音包络**，看两个量：

- **峰位**：包络峰相对拍点的偏移。越接近 0 越好（包络本身有约 +6ms 固有延迟，用已知真值的点击轨标定过）
- **峰背比**：拍点处平均包络 ÷ 全帧平均包络。越高说明能量越集中在拍点上

尺子先在**真值已知的合成点击轨**（120BPM，59 个点击，精确到采样点）上校准：

| 输入 | 峰位 | 峰背比 |
|---|---|---|
| 真值点击时间 | +6ms | 39.8 |
| librosa DP | -8ms | 36.1 |
| 旧 Node 检测器 | +30ms（≈早 24ms） | 29.6 |

标定有效，说明这把尺子能分辨 10ms 级的差别。

### 四种方法在 vibe.mp3 上的成绩

| 方法 | 拍数 | BPM | 网格抖动 | 峰位 | 峰背比 |
|---|---|---|---|---|---|
| 旧 Node 表 | 302 | 112.96 | 14.7ms | +40ms | 3.63 |
| librosa `beat_track`（DP） | 302 | 112.91 | **4.9ms** | -8ms | **5.45** |
| Beat-This `final0`（ISMIR 2024） | 253 | — | — | +20ms | 4.70 |
| **精修网格（当前采用）** | **301** | **112.91** | 5.8ms | **0ms** | **5.53** |

结论：

- 旧表的**相位整体早了 40ms**，而且网格抖动 14.7ms 是精修后的 2.5 倍——不是"略微不准"，是稳定地提前
- librosa 的 DP 跟踪把峰背比从 3.63 拉到 5.45，说明它抓到的才是真正的音头
- Beat-This 是当前学术 SOTA，但在这条混响极重的抖音抽轨上**漏检了 48 拍**（253/301），
  它的 DBN 后处理还依赖 madmom；它对单拍的位置与精修表差 19ms（82% 在 30ms 内），可作旁证
- 把 DP 的周期/相位拿来生成等距网格、再逐拍吸附到包络峰，得到 0ms 峰位 + 5.53 峰背比，是三者最优

### 工具选型备忘

| 工具 | 定位 | 在这台机器上 |
|---|---|---|
| **librosa** `beat_track` / `plp` | 纯 Python，Ellis DP，装一条命令 | ✅ 已用，pip 直装 |
| **madmom**（RNN + DBN） | 学术界的节拍/downbeat 标杆 | ❌ 0.16.1 在 Windows + 现代编译器下 `comb_filters.pyx` 编译失败（要 Cython<3 也过不去，官方基本只走 conda-forge） |
| **Beat-This**（ISMIR 2024） | 当前 SOTA，Transformer + DBN | ⚠️ 装得上（torch 2.14），但在这条轨上漏检严重；DBN 档位因缺 madmom 不可用 |
| **Sonic Visualiser** + Queen Mary Vamp（Bar & Beat Tracker） | 可视化、可手工微调，母带级校对的事实标准 | ⚠️ 图形界面，适合人眼最终确认，不适合脚本流水线 |
| **Ableton / Logic / Rekordbox** warp 标记 | 行业里做卡点最常用的做法：手动打点 | 需人工，但这是"最准"的上限 |

一句话：**自动化到 0ms 峰位已经够用了；要再往上，只能人工在 DAW 里对该轨打点。**

## 6. 排片时长建议

一屏时长取 **8.503s 的整数分之一**，切点自然落在圈头：

| 除数 | 每屏时长 | 适合 |
|---|---|---|
| 1 | 8.503s | 信息密度低的大标题 / 结论页 |
| 2 | 4.251s | **最常用**，一句话一个论点 |
| 3 | 2.834s | 三段并列、列表逐条 |
| 4 | 2.126s | 快剪冲击、数据对比 |
| 6 | 1.417s | 只适合短标签，文字撑不住 |

`build.mjs` 会在 ±0.5s 内把 `dur` 推到最近的击打点；写成 4.2 / 4.3 都能落上，
**但 5.0 这种"半圈"值只会被挪到拍点，不会帮你对齐圈头。**

## 7. 怎么用

**日常（99%）什么都不用做**——`build.mjs` 默认读 `assets/beats.json`：

```bash
node scripts/build.mjs --story story.json --out out/story.html
# [build] 卡点：BPM 112.91 · n/7 处切屏对齐击打 · 最大位移 0.07s
```

**查某个时间点的拍：**

```bash
node scripts/beats-info.mjs                # 概要 + 指纹校验
node scripts/beats-info.mjs --at 12.34     # → 最近的拍及偏差
node scripts/beats-info.mjs --snap 8.4     # → 对齐后的时长
node scripts/beats-info.mjs --check        # 只校验指纹，不匹配退出码 1
```

**需要再提高精度时（换了母带 / 新歌）：**

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv librosa soundfile
.venv/Scripts/python.exe scripts/refine-beats.py \
    --audio assets/bgm/vibe.mp3 --out assets/beats.json
```

它会打印旧表 / DP 原始 / 精修网格三者的峰位和峰背比，**看最后一行是否 0ms 附近、峰背比最高**。
`--dry-run` 只看不写。

## 8. 什么时候必须重跑

| 情况 | 动作 |
|---|---|
| 换歌 / 换母带 | 上面那条 `refine-beats.py` 命令（或 `beat.mjs` 快速版） |
| `beats-info --check` 报 mismatch | 同上（音频被替换过） |
| 精修后峰背比 < 2.5 | 这条音频没有可用节拍，别硬卡；用 `make-drum-track.mjs` 造基准轨，或每屏整秒 |
| 只想改文案 / 版式 | **不用碰节拍表** |

---

## 9. 不要做的事

- ❌ 手改 `assets/beats.json` 的 `onsets`——它是测量结果，不是配置文件。
- ❌ 用 `0.059 + k × 0.53142` 自己推拍点——真实音头有 ±31ms 浮动。
- ❌ 用 `beats.old96.json`（96BPM）或 `out/beats.node-113.302.json`（早 40ms）当基准。
- ❌ 用"24 秒压成一张波形/频谱图"判断有没有鼓——会把瞬态糊成噪声墙，直接误判成"没有鼓"。
  至少放大到 2 秒看。
- ❌ 换歌后不重跑就 build——会打警告，但警告不等于卡点正确。
